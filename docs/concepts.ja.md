# 考え方と使い方

Agentic Development Frameworkは、AIエージェントに開発を任せるリポジトリのための管理ツールです。「このリポジトリでは何を正とするか」を人とエージェントで一緒に決めて記録し、すべての変更をその記録に照らして進めます。コマンド名は`adf`です。

入口は英語の[`README.md`](../README.md)です。この文書と食い違う場合は英語版を正とします。対応言語と制限は[`docs/limits.md`](limits.md)、互換性として約束する範囲は[`COMPATIBILITY.md`](../COMPATIBILITY.md)にあります。

## 解こうとしている問題

エージェントに実装を頼めば、何かは実装されます。苦手なのは、必要な仕様がどこにも書かれていないと気づいて、手を止めることです。

たとえば「タスクを削除したら、添付ファイルも一緒に消すのか」。これはプロダクトとして人が決めることです。ところが仕様がないまま任せると、この問いは表に出ないまま、それらしいコードで埋まります。埋めたコードは判断のようには見えないので、レビューでも判断として扱われません。

誰かが決めた場合でも、答えはたいてい会話の中にしか残りません。会話は終わります。次の変更では同じ問いをもう一度尋ねるか、尋ねないまま別の答えを出します。

このツールが作るのは、次の状態です。

- 決めるべき問いが、埋もれずに人の前に出てくる
- 人が決めた答えが記録に残り、同じ問いが二度と戻ってこない
- 実装は記録された規範に照らして検証され、検証は実装した本人以外が行う

## 中心にある2つの記録

- **Contract** — このリポジトリで今守ると決めた規範。内容に加えて、誰の権限で決まったのか、何をもって満たされたとするのかを持ちます。
- **Decision** — その規範をなぜ選んだのかという、判断の記録。

先ほどの例なら、人が「添付ファイルも消す」と決めた経緯がDecisionに残り、「タスクの削除は添付ファイルも一緒に削除する」という規範がContractの条項になります。次に削除まわりを触る変更は、尋ね直すのではなく、この条項に従って進みます。

Contractは人とエージェントが一緒に作ります。エージェントがコードを調べて規範の足りない箇所を見つけ、選択肢とその影響を並べ、どれを推すかまで示します。決めるのは人です。エージェントは決める立場になれず、人は問いを一から組み立てずに済みます。

Contractは変更のたびに増えます。障害から学んだことはテストを伴う条項になり、1つの機能を超えて効くと分かった規範は上位の層へ移ります。変更が終わるたびに、リポジトリは自分自身について前より多くを知っています。この蓄積が、このツールで得られるものです。

## 変更の流れ

変更は`adf change init`で作ります。以降は`adf next`が「次にやること」を1件ずつ返します。エージェントはそれを実行し、MCPの`adf_submit`で結果を提出して、また次を受け取ります。作業の順番を決めるのはエージェントではなく`adf`です。

最初の作業は影響評価です。変更の目的から、影響がある対象とリスクを実装前に整理します。結果は次の3種類を明示します。

- `impacts-identified`：影響を特定できた
- `no-impact`：確認した結果、影響がない
- `inconclusive`：判断に必要な情報が足りない

コードがないことを、影響がないこととは扱いません。新規プロジェクトでは、最初の変更依頼から実現しようとしている振る舞いを特定し、その変更に必要な最小限のContractを作ってから実装へ進みます。

```text
   adf change init
        │
        ▼
┌─▶ adf next ─── 次の作業1件と、必要な文脈だけ
│       │
│       ├─ Analyst    影響と仕様を分析する。足りない規範はContractに書き、
│       │             決められない問いは人へ渡し、答えを記録する
│       ├─ Builder    実装し、必要な条項の証拠を記録する
│       └─ Challenger 実装の前後で反証する
│       │
└───────┴─ adf_submit ─── 結果を検証して保存し、状態を進める
        │
        ▼
   ready-to-merge
```

作業は3つの役割に分かれ、役割ごとのスキルを`project init`が配置します。

| 役割 | スキル | 担当 |
|---|---|---|
| Analyst | `$adf-analyst` | 仕様の分析。検出候補の確認、Contractの記入、人への判断依頼と回答の記録 |
| Builder | `$adf-builder` | 実装と、必要な条項の証拠の記録 |
| Challenger | `$adf-challenger` | 実装前と実装後の反証 |

Challengerが行う反証とは、依頼・規範・実装が間違っている可能性を、作った本人とは別の立場から探して確かめる作業です。実装後の反証は、実装した文脈から独立した文脈で行います。同じ文脈での自己レビューを反証として記録することはできません。

変更は次の状態を通ります。各状態でやることが、そのまま`adf next`から発行されます。

| 状態 | やること |
|---|---|
| `needs-impact-assessment` | 実装前に、変更の目的から影響を評価する |
| `needs-post-build-impact-assessment` | コードや規範が変わったため、影響を評価し直す |
| `needs-analysis` | 検出された候補を確認し、要件を分析する |
| `needs-human-decision` | 決められない問いを、選択肢と推奨を添えて人へ渡す |
| `needs-decision-recording` | 人の答えをDecisionとContractへ記録する |
| `needs-pre-build-challenge` | 実装前に、依頼・根拠・Contractを反証する |
| `ready-to-build` | 実装する |
| `needs-evidence` | 対象となる`direct`または`inherited`条項の証拠を記録する |
| `needs-post-build-challenge` | 実装後に、独立した文脈から実装を反証する |
| `ready-to-merge` | なし。完了 |

変更がいまどの状態にあり、なぜそこにいるのかは、`adf explain <変更ID>`で確認できます。変更ごとの記録は`.adf/changes/<変更ID>/`に残ります。

ResultとEvidenceの鮮度は、それぞれが確認したコード、Contract、Decision、Changeの内容で判定します。実行時のGit revisionは追跡情報として残しますが、ADFのResultやEvidenceだけをcommitしてHEADが進んでも、確認対象の内容が同じなら再確認は要求しません。

Contractまたは条項の`evidence_mode`で、検証に掛ける費用を選べます。`direct`は、その条項を何によって確認したかをEvidenceの`claims`へ明示します。`inherited`は、別の条項と共通するテストや実証結果を再利用できます。`review`はEvidenceを要求せず、独立したChallengerによる反証の対象にします。設定のない既存Contractは従来どおり全条項を`direct`として扱います。新しいContractでは、全体を`review`として、事故やデータ破損などにつながる条項だけを`direct`または`inherited`で上書きできます。

## 文脈の再利用と実行コスト

`adf next`は、各作業に必要な文脈だけを組み立てます。影響評価には、リポジトリ、Contract、Decisionの索引と、過去の影響評価を最大3件まで渡します。評価が確定した後の実装には、その評価結果と、対象に合う規範やコードだけを渡します。後続の作業がリポジトリ全体を調べ直す必要はありません。

各作業には、実行環境へ向けたモデルの推奨も含まれます。影響評価には通常、軽量なモデルを推奨します。ただし、影響なしと結論付ける場合、根拠が矛盾する場合、セキュリティ、プライバシー、決済、元に戻せないデータ変更の可能性がある場合は、精度の高いモデルへの切り替えを勧めます。ADF自体はモデルを選ばず、LLMも実行しません。

実行環境がすでに把握している処理時間、モデル名、入出力Token数、ツール呼び出し数、再試行回数は、`adf_submit`で任意に記録できます。外部Runnerは`adf_begin_execution`と`adf_complete_execution`を使い、Result提出後に確定したToken数や、失敗・中断した実行も追記できます。外部実行では、キャッシュ作成Token、キャッシュ読取Token、推論Token、実行環境が報告した米ドル費用も記録できます。この実行RecordはADFの状態、Result ID、鮮度、Evidence検証には影響しません。同じResultに提出時の計測値とRunnerの完了Recordがある場合は、Runnerの値だけを集計します。

ADFは文脈のバイト数だけを計算します。計測のためにLLMを起動したり、料金を推測したりしません。不明な値は不明のまま残します。

記録はMCPの`adf_execution_log`、または次のコマンドで確認できます。

```sh
adf execution-log <変更ID> --format json
```

### Codex・Claude Code Runnerの試作

`adf-codex-runner`と`adf-claude-runner`はADF本体とは別の任意ツールです。ADFが自動で起動することはありません。ユーザーが利用しているメインセッションが、独立実行を必要とする場合だけ、使用中のエージェントに合うRunnerを呼び出します。

最初の版はChallenger Actionだけを受け付けます。Codexでは`codex exec --ephemeral`、Claude Codeでは`claude -p --no-session-persistence`を毎回起動します。Runnerは起動前にAction IDとContext digestを照合し、独立したエージェントも自分のMCPセッションで`adf_next`を実行します。ContextはADFが生成した完全な値を使い、メインセッションの会話要約は渡しません。会話で決まった要求は、独立実行の前にChange、accepted Contract、accepted Decisionへ記録する必要があります。

```sh
adf-codex-runner run \
  --project /path/to/project \
  --change change.example \
  --expected-action action.example \
  --expected-context sha256:...
```

Claude Codeでも、同じ識別子を渡します。

```sh
adf-claude-runner run \
  --project /path/to/project \
  --change change.example \
  --expected-action action.example \
  --expected-context sha256:...
```

RunnerはCodexのJSONLやClaude Codeの完全なJSON応答をリポジトリへ保存しません。完了時に報告されたToken数、Claude Codeが報告した費用、処理結果だけをADFへ記録します。Claude Codeでは、プロジェクトのMCP、Skill、`CLAUDE.md`を読む必要があるため`--bare`を使いません。会話は`--no-session-persistence`で保存しません。現在の署名付き配布物にはRunnerを含めないため、試作を使う場合は対象のRunnerをソースからビルドします。

## 使ってみる

`adf`の入手方法は英語READMEの「Installing」にあります。まだリリースを公開していないため、現時点ではRustでビルドします。

用意できたら、Gitリポジトリで初期化します。

```sh
adf project init --project /path/to/project
```

設定ファイル、固定されたFramework Release、3つのスキル、進め方ガイドの`docs/adf/README.md`、`AGENTS.md`への追記が置かれます。既存のファイルは上書きされず、コミットも自動では行われません。

既にコードがあるリポジトリでは、まず検出器に読み取れるものを一覧させ、人がレビューしてから確定します。データベースへの書き込みに見える名前も、レビューを通るまでは候補のままで、事実としては扱われません。

```sh
adf project observe --project . --output .adf/repository-observation.draft.yaml
# 一覧に論理ID、担当者、根拠となるDecisionを記入する
adf project validate-bindings --draft .adf/repository-observation.draft.yaml
adf project promote-bindings --draft .adf/repository-observation.draft.yaml
```

あとは変更を作り、`next`に従って進めます。

```sh
adf change init change.first-feature \
  --title "最初の機能" \
  --intent "この変更が存在する理由"

adf next change.first-feature
```

エージェントには、同じ操作をMCPサーバー経由で使わせます。

```sh
adf mcp --project /path/to/project
```

## Contractの階層

規範には、1つの機能にだけ効くものと、リポジトリ全体に効くものがあります。Contractはこれを層に分けて持ちます。

```text
Project Contract          リポジトリ全体の原則と、人が決めるべき領域
  ├─ Domain Contract        用語、エンティティ、関係、状態の移り変わり
  ├─ Capability Contract    複数の機能にまたがる振る舞い
  ├─ Architecture Contract  責務、依存の向き、参照実装
  ├─ Data Invariant         どの操作順序でも常に満たす状態
  └─ Operation Contract     1つの読み書き。前提、影響、失敗、再試行

Feature Contract          今回の変更で足すもの
  └─ governing_contracts ─▶ 適用する上位Contract
```

Feature Contractは、上位Contractの写しでも上書きでもありません。今回の変更で足す差分だけを書き、どの上位Contractが効くのかを`governing_contracts`で指し示します。

先ほどの添付ファイルの例で、「子レコードは親と一緒に消える」がタスクに限らない決まりだと分かったとします。その規範はFeature Contractに留めず、データ全体を担当するData Invariantへ移します。以降はどの機能の変更にも最初から効きます。効く範囲に合った層へ移しておくことが、同じことを学び直さずに済む理由です。

このうちデータの2層は、個々のAPIのテストでは守りきれない整合性を受け持ちます。

- **Data Invariant** — 操作の種類や順序に関係なく常に満たす状態。「親を持たない子レコードが存在しない」「テナントの境界を越えて参照できない」など
- **Operation Contract** — 1つの読み書きの振る舞い。前提条件、変更する対象、外部への作用、失敗しうる箇所、再実行したときの結果

反証では、同じデータへ書き込む経路を並べ、単体では正しくても組み合わせるとInvariantを破る順序を探します。重複、逆順、並行実行、部分的な失敗、移行中の新旧混在も試します。具体的な観点は、`adf-challenger`スキルが参照する文書にまとめてあります。

## この進め方が信頼できる理由

次の作業を決め、提出された結果を検査するのは`adf`本体です。以下ではこれを制御基盤と呼びます。各段階を決めるのがエージェントの記憶ではなく制御基盤なので、過程を口先で押し切ることができません。具体的には次のとおりです。

- **作業の順序は、記録から計算する。** 制御基盤がリポジトリの記録から次の作業を導き、作業の識別子は導出元のダイジェストになります。手順を忘れて飛ばすことも、状態が求めていない手順を作り出すこともできません。途中で処理が落ちても、同じ記録からは同じ作業にたどり着きます。
- **仕様の根拠にできるものは、4種類に決まっている。** 要件を満たしたと報告するには、受理済みContractの条項、依頼文に明示された要求、記録された人の判断、受理済みDecisionのいずれかが要ります。エージェント自身の推論、既存コード、テストの現状は、事実の裏付けにはなっても仕様の根拠にはなりません。どれも示せない提出は受け付けられません。
- **コードの挙動は、説明ではなく読み取る。** 検出器が16言語のソースを構文解析します。説明のつかない呼び出しは、見逃さずにその変更を止めます。名前だけで分類することもしません。`save`や`execute`が何を指すかはフレームワークごとに違うので、人がレビューした対応付けが要ります。
- **前提が変わった結果は、やり直しになる。** 提出された結果は、根拠のダイジェストに結び付いています。Contract、コード、根拠のどれかが変われば、それに依存していた結果は古いものとして扱われ、やり直しを求められます。コードから離れたContractが黙って通り続けることはありません。
- **自分の作業を自分で検証しない。** 実装と反証は別の役割で、実装後の反証は独立した文脈で行います。この線引きは、プロジェクトが固定する署名済みのFramework Releaseに入っており、プロジェクト側で検証済みとみなす範囲をこっそり広げることはできません。

制御基盤が検査しないことも決まっています。見るのは構造、参照、状態、ダイジェスト、検出できた範囲までで、書かれた内容が正しいかどうかは判定しません。誤ったことを書いたContractは、そのまま受理されます。内容の正しさを確かめるのは反証と人のレビューの仕事です。何を検査しないのかがはっきりしていることが、残りを信頼できる理由になります。

## リポジトリに残る記録

| 場所 | 残るもの |
|---|---|
| `contracts/` | 現在有効な規範。何を守るか |
| `decisions/` | 規範を決めた理由と、その変更履歴。なぜそうしたか |
| `evidence/` | 条項に対応するテスト、実証、反証の結果、残っているリスク |
| `probes/` | 外部プラットフォームの挙動を実証する実行物 |
| `docs/adf/` | 進め方ガイド、既存文書とContractの対応、導入時の調査報告 |
| `.adf/changes/<変更ID>/` | 変更ごとの記録、発行された作業の結果、判断依頼 |
| `.adf/config.yaml` | 正本の場所と、観測結果の置き場所 |
| `.adf/framework.lock` | 使用するFramework Releaseの固定 |
| `.adf/repository-observation.yaml` | コード上の識別子と論理IDの、レビュー済みの対応付け |
| `.agents/skills/` | 3つの役割のスキル |

現在有効な規範は`docs/`に留めず、`contracts/`へ上げます。`docs/adf/`は案内と索引です。

## 制御基盤・エージェント・人の分担

| 担当 | 役割 |
|---|---|
| 制御基盤 | 次の作業を決める。構造、参照、状態、ダイジェスト、証拠の不足を機械的に検査する |
| エージェント | リポジトリを調べ、Contractを書き、選択肢を整理し、実装し、内容の面から反証する |
| 人 | 根拠のないプロダクト判断、リスクの受け入れ、優先順位を決める |

すべてを人へ丸投げするわけではありません。エージェントは既存の記録から解決できる問いを自分で処理し、決まっていない問いだけを、選択肢と影響と推奨を添えて人へ渡します。
